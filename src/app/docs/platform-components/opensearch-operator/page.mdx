# OpenSearch: Reclaim the Stack OpenSearch Operator

For OpenSearch we use our own Kubernetes operator. It's tightly scoped to how Reclaim the Stack runs search clusters, and it's written in Ruby like the rest of our tooling.

Github: https://github.com/reclaim-the-stack/opensearch-operator<br />
Documentation: [OpenSearch Operator](/docs/opensearch-operator/introduction)

## Architecture Decision Record

We started out with the official OpenSearch operator, but ran into enough problems that writing our own turned out to be the better option. Keeping the scope narrow is what makes that sustainable: the operator does what we need, and does it carefully, rather than trying to cover every possible OpenSearch topology.

### Pros

- Runs current OpenSearch versions
- Random passwords for all built-in users, and a ready to use connection URL in a Secret
- Declarative snapshot management: S3 repositories and snapshot policies are part of the cluster spec
- Health gated rolling restarts, safe scale downs and a PodDisruptionBudget which follows cluster health, so neither changes to the spec nor node drains during Kubernetes upgrades take down more than one node at a time
- Status conditions which work with `kubectl wait` and Argo CD health checks
- Prometheus metrics and a Grafana dashboard
- A small codebase (around 1,700 lines of Ruby) which we can read and change ourselves

### Cons

- Deliberately limited scope: all nodes of a cluster are identical cluster manager eligible data nodes, there's no support for custom users and roles, and clusters need at least 3 nodes
- The REST API runs without TLS, which assumes clusters are only reachable on the private network
- The disk size of a cluster can't be changed after it was created (since our platform uses local storage, actual disk size is always equal to the space remaining on disk in any case)

### Alternatives Considered

#### Official OpenSearch Kubernetes Operator

The [official operator](https://github.com/opensearch-project/opensearch-k8s-operator) was our first choice. In practice we hit too many issues:

- It couldn't deploy OpenSearch versions released after early 2024
- Its certificate generation didn't work, and would only have created certificates with a one year TTL and no rotation
- No generated passwords for the built-in users
- A large number of open bugs with little movement on them
- Admin credentials readily available on disk in the OpenSearch pods

#### Elasticsearch with Elastic Cloud Kubernetes

If you prefer Elasticsearch, the platform supports it through [Elastic Cloud Kubernetes](/docs/platform-components/elasticsearch-operator), which is a well made operator. OpenSearch is the Apache 2.0 licensed fork of Elasticsearch, and the one we run for new workloads.

## Creating a cluster

Add the OpenSearch generator template to your DevOps repository once (see [Usage](/docs/opensearch-operator/usage#creating-a-cluster)), then run `k generate resource <application-name> opensearch`. This adds an `OpenSearch` resource under `applications/<application-name>/templates` and outputs the Helm values to add to `applications/<application-name>/values.yaml`.

## Connecting to a cluster

Every cluster gets a Secret called `opensearch-<cluster-name>-credentials`, whose `admin_uri` key holds a connection URL for applications inside Kubernetes:

```yaml
env:
  - name: OPENSEARCH_URL
    valueFrom:
      secretKeyRef:
        name: opensearch-<cluster-name>-credentials
        key: admin_uri
```

From your local machine:

- `k opensearch:url <cluster-name>` outputs the internal URL
- `k opensearch:dashboards <cluster-name>` opens OpenSearch Dashboards, which every cluster gets
- `k opensearch:overview <cluster-name>` shows the health, size and JVM usage of a cluster

See the [OpenSearch Operator documentation](/docs/opensearch-operator/introduction) for installation, the full cluster spec, snapshots, monitoring and how the operator handles restarts, scaling and node drains.
